## 内存根因与修复

此前应用通常在约 18 次进入/退出后被系统终止；页面计数归零不能证明底层资源回收。[调查记录](../android-memory/investigation.json) 保留失败迭代。

- JavaScript 层：断开销毁设备仍挂起的 lost 订阅，原生错误回调只保留弱引用；一次性回调执行后清除捕获对象，避免已完成回调继续保留设备和管线。
- 原生层：unconfigure/drop 时释放 `ContextReadBack` 纹理；恢复被注释的 `shader_module_drop`；释放 `finish()` 后的命令编码器。wgpu 29 的 `finish()` 会创建独立 command-buffer 句柄，原先 `open=false` 的分支跳过了编码器释放。
- 转换器保持按需创建，离开页面时完成 GPU/宿主释放后再拆除共享视图。

[最终循环报告](lifecycle.json) 在同一进程完成 50 次真实编辑器、Engine/GPU 及原生视图创建/退出，没有缩短次数或每轮重启。每次确认原生视图已拆除、Engine destroyed、共享节点/资源/订阅及帧回调归零。[内存观测](memory.json)：第 21～50 次 native heap 31.7～37.6 MiB、进程 PSS 168.9～180.0 MiB；系统可用内存在 2.57～3.00 GiB 范围波动，未再逐轮下降约 200 MiB。末轮弱引用仍可观察到最近 3 组对象，旧对象随后续 GC 回收，未随 50 次累计。

[诊断包](../android-memory/diagnostic-summary.json) 也独立通过 50 次，并观察到编码器归零、着色器模块不再累积。诊断 logcat 在第 31 次设备销毁附近意外结束，因此资源 trace 是部分证据；完整 50 次来自设备持久化报告。最终包已移除临时原生日志。上述结果不等于完整 GPU 堆计量或无限时长无泄漏证明。

## 共享 UI 性能

减少值/文字更新时的原生属性提交：不重复写入未变化的尺寸、字体、颜色和裁剪；只有布局、显隐、页签、弹窗等相关变化才重新处理整页关系。无障碍值继续随内容更新，表单标签/错误关联、主题、原生视图重建和键盘行为保留。

[同机性能报告](performance.json) 使用同一最终 APK，旧/新入口交替各 3 轮，每轮 100 次语义操作；每项数值为三轮 p95 的中位数。实际 surface 为 **113×64**，选择器动画不计入 handler。

| 指标 | 旧入口 | 共享入口 | 比例 | 结论 |
| --- | ---: | ---: | ---: | --- |
| UI handler | 3.779 ms | 3.731 ms | 0.987 | 通过 |
| 编译后呈现 | 68.258 ms | 69.610 ms | 1.020 | 通过 |
| 帧回调节奏 | 18.601 ms | 18.433 ms | 0.991 | 通过 |

原门槛保持 p95 比例 ≤ 1.10、各路径三轮 max/min ≤ 1.10。handler 波动分别 3.91% 和 4.03%；其他两项波动更小。结论是共享页面与旧入口基本持平并通过预算，不把微小差异解释成显著加速，也不将帧回调节奏称为 GPU timestamp。
